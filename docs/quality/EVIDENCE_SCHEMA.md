# Implementation and Requirement Verification Evidence Contract

Evidence manifests live below `docs/quality/evidence/`. The quality checker rejects absolute paths, repository escapes, escaping symlinks, empty files, arbitrary non-JSON files, and manifests with missing fields. Evidence values are claims only. Canonical Requirement, Change, Slice, coverage, and Acceptance authority comes from the validated repository scope mapping; executable verification authority comes only from `docs/quality/verification-targets.json` and the trusted runner.

## Implementation Attestation

Every `IMPLEMENTED_UNVERIFIED` row references exactly one schema-v2 JSON Implementation Attestation in an `implementation/` directory. Required fields are `schema_version`, `requirement_id`, `change_id`, `slice_id`, `coverage`, `implementation_stage`, `implementation_refs`, `test_refs`, `test_bindings`, `required_acceptance_ids`, `verification_targets`, `execution_receipts`, `source_fingerprint`, and `created_at`.

The checker independently requires one canonical `FULL` owner, validates the claimed scope and required Acceptance IDs against that owner, and requires the active Change/Slice to equal the owner on every run. `PARTIAL`, `DEFERRED`, `SCOPE_GUARD`, later-Slice, and cross-Change entries cannot enter or retain the intermediate state. There is no committed/persisted/grandfather exception: every existing `IMPLEMENTED_UNVERIFIED` row is fully revalidated against the current active scope, attestation, sources, target definitions, structured collection, and actual execution.

Each test binding contains exactly `target_id`, exact pytest `test_nodeid`, `requirement_id`, and `acceptance_ids`. The pytest collection plugin reads repeatable `quality_binding` markers from collected items; comments and arbitrary source strings create no binding. Collected markers must name known Requirements and their own Acceptance IDs, and the union of the canonical target nodes covers every required Acceptance. The trusted runner then executes those exact node IDs. It captures the real subprocess return code and output hashes; manifest `command`, `exit_code`, or log claims, if retained as informational metadata, have no authority.

`verification-targets.json` allowlists repository-owned target IDs, scope, stage, expected verification level, runner, setup, exact arguments, test nodes, and receipt paths. Manifests can reference only target IDs and cannot submit shell text. Every `FULL` Requirement in the active Change/Slice has a distinct `REQUIREMENT_VERIFICATION` target path; `IMPLEMENTATION` targets never substitute for it. The registry checker also requires the union of those targets to cover every mandatory Acceptance and validates Requirement/Acceptance ownership and the declared verification level.

A schema-v2 runner receipt records the verification-base HEAD, target and registry hashes, Requirement and Acceptance IDs, verification stage and level, source fingerprint, exact argv, collection and execution return codes, execution timestamp, working directory, collected bindings, per-node outcomes, and stdout/stderr hashes. For Requirement Verification, the runner accepts only canonical target IDs, resolves the sole matching Implementation Attestation itself, and never accepts evidence-supplied commands or fingerprints. A source or target-definition change invalidates the receipt. A retained Requirement Verification receipt must bind the same stable HEAD named by its Requirement Verification evidence. Retained receipts are audit artifacts; the checker still performs a fresh canonical execution before authorizing a state.

Implementation and test references are normalized repository-relative, existing, regular, and non-empty files. The attestation fingerprint is SHA-256 over the following aggregate: `requirement_id`, canonical `change_id`, canonical `slice_id`, and `coverage=FULL`, each encoded as `field`, NUL, `value`, newline; then each sorted unique implementation/test reference encoded as `relative_path`, NUL, the file SHA-256 in lowercase hex, newline. Changing the Requirement/scope claim or any referenced source invalidates the attestation.

## Requirement Verification Evidence

`PASS` evidence is a separate schema-v2 JSON manifest. Required fields are `schema_version`, `requirement_id`, `acceptance_ids`, `change_id`, `slice_id`, `verification_stage`, `result`, `verified_at`, `git_head`, `implementation_refs`, `test_refs`, `verification_targets`, `test_bindings`, `execution_receipts`, `artifacts`, `source_fingerprint`, `implementation_attestation_ref`, and `implementation_attestation_hash`.

For a `PASS`, `verification_stage` and `result` are `REQUIREMENT_VERIFICATION` and `PASS`. Canonical Requirement Verification targets must belong to the same Requirement/Change/Slice, cover every required Acceptance, collect the declared structured bindings, and actually pass under the trusted runner. References are repository-relative, existing, regular, and non-empty files.

`git_head` identifies the source-state commit that entered Requirement Verification and must equal the repository's current HEAD. That commit's Traceability row must be `IMPLEMENTED_UNVERIFIED` and reference exactly the attestation named by `implementation_attestation_ref`. The content SHA-256 must equal `implementation_attestation_hash`; Requirement, canonical owner, `FULL` coverage, implementation/test refs, and source fingerprint must all match the still-valid attestation. A changed source, substituted attestation, or direct `UNIMPLEMENTED → PASS` jump fails.

At the `REQUIREMENT_VERIFICATION` stage, `VERIFICATION_STATE.json` supplies the repository-controlled `active_change` and `active_slice` and lists every independent manifest in `independent_requirement_verification_evidence`. The checker validates the machine-readable registry against the Requirement Index, Acceptance Contract, PLAN, and current OpenSpec proposal/tasks/capability specs. Registry coverage meanings are fixed: `FULL` grants eligibility only in that exact Change/Slice; `PARTIAL` records an incomplete contribution; `SCOPE_GUARD` records a gate rather than a Slice business outcome; and `DEFERRED` assigns no current completion authority.

Machine-verifiable facts are scope ownership, file existence and hashes, target/AC mapping, pytest collection metadata, exact executed node IDs, subprocess outcomes, and receipt freshness. Reviewer independence is a process-level property established by the separate Requirement Verification session. A repository-editable `reviewer_gate` field may be retained as informational audit metadata, but the checker never treats it as authorization and does not claim to prove reviewer identity.
